# APEX AutoLab Reception v1.1.0

Дата підготовки: 02.10.2026. Перевірений локальний MVP для приймання авто на СТО. Автор проєкту: Яковенко Олександр Володимирович, КН-41.

## Призначення випуску

Ця версія фіксує робочу основу Front-end і Back-end для завершення навчальної практики та подальшого розвитку. Основна довгострокова мета — використання на реальному автосервісі. Плануються періодичні оновлення; поточний випуск не є завершенням розвитку продукту.

Базовий коміт функціональності: `a5b87c9a02121736c1e5f549f2de6ea2b92d0223` (`main`). Гілка випуску: `release-v1.1.0`. Позначення випуску: `v1.1.0`; анотований тег потрібно опублікувати окремо після фіксації цієї гілки. Наявність тегу перевіряється в GitHub, а не лише за цим документом.

## Основні можливості

- Облік клієнтів і автомобілів, пошук за номером, VIN, ім’ям або телефоном у відповідних довідниках.
- Приймання авто, чернетка наряду, історія статусів, запобігання другому активному наряду на те саме авто.
- Заборона готовності без клієнта, контактів, звернення та явного підтвердження оператора.
- Графічний інтерфейс, світла, темна й системна тема, адаптація до вузьких екранів.
- REST API, сесія одного оператора, CSRF, валідація, обмеження невдалих входів.
- Локальний OCR фотографії номера через Tesseract із ручною перевіркою результату.
- Фото в наряді, копіювання SQLite разом із вкладеннями, офлайн-відновлення архіву.

## Зміни під час підготовки релізу

Видалено відстежуваний службовий файл macOS `.DS_Store`. Додано цей опис і `v1.1.0-validation.json`. Уточнено мету подальшого розвитку в README. Бізнес-логіка, API та схема SQLite не змінені від базового коміту.

## Результат перевірки 02.10.2026

- 46 pytest-тестів пройдено, 7.75 с.
- 25 браузерних перевірок пройдено в Chromium/Linux зі справжнім Flask/Waitress API та тимчасовою SQLite.
- Перевірено приймання, CRUD, статуси, валідацію, сесію, CSRF, фото, копіювання, OCR, стани помилки/очікування та ширини 1200/736/390/320 px.
- В окремих сценаріях мережеві відмови, CSRF-відмова й OCR/503 імітуються тестовим runner. OCR також викликано реально на синтетичному фото.
- Python 3.12; залежності — requirements-lock.txt. Робочі клієнтські дані не використовувалися.

Результати стосуються перевіреного коду, а не всіх майбутніх оновлень. Користувач повідомив про базову роботу застосунку й OCR на своєму Mac; повної приймальної перевірки macOS/Windows та реальних фото цей факт не замінює.

## Встановлення та оновлення

Для чистого встановлення використовуйте README. Для наявного встановлення спочатку зупиніть сервер, створіть перевірену резервну копію даних та збережіть попередній код і lock-файл. Оновлюйте код зі збереженням `instance/` або зовнішнього `APEX_DATA_DIR`. Повторно створювати оператора не потрібно. Середовище `.venv` створюється на цільовій машині, не копіюється між ОС.

Версія схеми — 1. Міграцій у цьому випуску немає. `/api/health` усе ще повертає `version: "1.0.0"`: це старе значення API, а не ідентифікатор комплекту. Для точного визначення встановленого випуску використовуйте Git commit та тег.

## Обмеження та подальший розвиток

Один локальний оператор; сервер лише на `127.0.0.1`. Адаптивність інтерфейсу не означає доступ із телефона через мережу. Немає інтеграції ROApp, відеопотоку, автоматичного встановлення особи власника, ролей, автоматичних оновлень чи міграцій. Архіви даних не зашифровані.

Перед реальним пілотом потрібні перевірка відновлення на цільовому комп’ютері, реальні фото, тривала робота й захист даних засобами ОС. Наступні релізи мають містити опис змін, результати тестів і правила сумісності. Старі опубліковані теги не пересуваються; для змін створюється нова версія. Сам репозиторій не переводиться в режим GitHub Archive, оскільки розробка продовжується.

## Архів коду і копія даних

ZIP вихідного коду фіксує програму та документацію; він не містить робочої БД, пароля, фотографій клієнтів чи `.venv`. Дані резервуються окремо через функцію Backups або `manage.py backup`. Для відкату потрібні відповідний код, залежності та сумісна копія даних.
